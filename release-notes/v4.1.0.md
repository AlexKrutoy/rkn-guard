## Адаптивный щит на nftables

Второй контур защиты рядом со списками подсетей. Списки ловят известные сканерные сети, щит — всех остальных: считает новые соединения в ядре и банит источник на время.

```
sudo rkn          # пункт «Адаптивный щит»
sudo rkn-guard guard apply --level enhanced --ports 443,22
sudo rkn-guard guard status
sudo rkn-guard guard top
```

### Что умеет

- Профили `relaxed` 900/10м · `basic` 600/15м · `enhanced` 300/1ч · `strict` 100/6ч, плюс `custom --rate/--ban-time`.
- Считает соединения через conntrack, а не парсинг логов: работает с Xray, sing-box, 3x-ui и любым другим ядром.
- Своя таблица `inet rkn_guard_dynamic` — чужие правила `iptables`, `nftables`, `ufw` не трогаются.
- Баны и настройки переживают перезагрузку, срок бана восстанавливается.
- `guard rollback` снимает таблицу, службу и состояние без остатков.
- Внешние фиды адресов дополняют чёрный список, но не могут отменить белый.

### Защита от самострела

- Белый список идёт первым правилом: loopback, приватные сети, CGNAT `100.64.0.0/10`, свои адреса через `guard allow add`.
- Автобан работает только по одиночному адресу — подсеть забанить нельзя.
- У бана всегда есть срок: бессрочных банов нет.
- Адрес текущей SSH-сессии попадает в белый список до применения правил. Если он всё же внутри блокируемой подсети, щит не применяется и объясняет причину.

### Проверено

- `go build ./...`, `go vet ./...`, `gofmt -l` — чисто.
- Тесты рендера правил и настроек: белый список выше бана, подсеть отклоняется, бан со сроком, переопределение через `allow`, отказ при риске отрезать сессию.
- `tests/integration/guard_shield.sh` на живом nftables: apply, запрет бана подсети, бан, unban, чистый rollback.
- `tests/menu_terminal.py`, `live_logs.py`, `update_schedule.py`, `extra_lists_menu.py`, `attack_stats.py` — зелёные после перенумерации пунктов меню.
- CI: unit, lifecycle и упаковка на пяти дистрибутивах.
